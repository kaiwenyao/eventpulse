# 人工验收流程：购物车、历史订单与钱包流水

本文给出一条可以在本地环境里亲手走一遍的验收路径。从零开始大约需要 15 分钟。

前置条件：本机已装 Docker。所有命令在仓库根目录执行。

## 0. 准备环境

```bash
cp .env.example .env        # demo 用默认密钥即可
make down                   # 清掉旧容器和数据卷，从干净状态开始
make up                     # 构建并启动：postgres / redis / kafka / seeder / api×2 / worker×2 / frontend
make ps                     # 等待全部 healthy，seeder 成功退出
```

打开 http://localhost:3000 ，用 `user@eventpulse.dev` / `User123456` 登录。
该账号带有演示订单和一条「期初余额」流水；余额、订单、流水在播种时就是一致的。

## 1. 购物车

1. 打开任意一个「已发布、未开始」的活动详情页，选择数量 2，点 **加入购物车**（不会扣款，也不会减少余票——可回列表核对余票数）。
2. 顶栏进入 **购物车**：能看到该活动、单价、小计。回到同一个活动再加 1 张 → 数量合并为 3（同一活动只有一行）。
3. 再挑一个活动加购。试着把某个活动数量调到超过单次限购 → 加号被禁用；直接调数量也一样。
4. 取消一个活动的勾选，点 **清空购物车** 前先试 **移除** 单项。
5. 刷新页面、退出重新登录（或换浏览器）→ 购物车还在。

## 2. 批量结算（整次成功 / 整次回滚）

1. 记下当前余额（个人中心）。勾选若干活动，点 **结算勾选项**。
2. 成功后跳到「我的预订」：每个活动一张独立订单，状态 CONFIRMED；个人中心余额恰好减去勾选总价；**余额明细**里每张订单各有一条「下单扣款」，充值 / 扣款后的变动后余额逐行核对得上。
3. **整次回滚**：往购物车加一个便宜活动和一个贵活动，充值少量余额使总额不够，再结算 → 报「余额不足」；购物车原样保留、余额未动、订单没有出现。
4. **库存不足回滚**：让勾选项里包含一个余票不足的活动（可先用另一个账号买走大部分票），结算 → 报错并回滚，其他勾选项也没有被买入。
5. **价格变化需确认**：加购后由主办方账号改价（或在数据库改 `events.price_cents`），回到购物车 → 显示「价格已变化，需重新确认」；点结算被拒绝；点「按新价格结算」确认后才会按新价成交。
6. **幂等**：结算成功后在 Network 面板里找到 `/api/cart/checkout` 请求，复制它的 `Idempotency-Key`，用 curl 带同一个键重放——返回同一批订单，余额不再变化：

   ```bash
   curl -s -X POST http://localhost:3000/api/cart/checkout \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer <token>" \
     -H "Idempotency-Key: <复制的键>" \
     -d '{"items":[{"itemId":<原itemId>,"quantity":<原数量>}]}'
   ```

## 3. 历史订单

1. 进入 **我的预订**：默认列出全部订单（含已取消），按时间倒序。
2. 用状态筛选（CONFIRMED / CANCELLED）、时间范围过滤；在搜索框输入订单号或活动名关键字。
3. 翻页：页码在服务端计算（`?page=&size=`）。
4. 打开一张已取消订单的详情：能看到下单单价、实付金额、已退款金额、取消时间，以及（购物车结算的）同次结算的其他订单。
5. 取消一张 CONFIRMED 订单 → 状态变 CANCELLED、票作废、余额退回；再点取消 → 明确报错，不会重复退款。
6. 对一张票已核销的订单（演示数据里有）尝试取消 → 提示「已有电子票核销入场，不能退款」。
7. 越权：复制另一个用户的订单详情 URL（换订单 id）→ 403/404，看不到别人的订单。
8. 断网（DevTools Offline）后刷新列表 → 显示「加载失败」+ 重试按钮，而不是「暂无订单」。

## 4. 钱包流水

1. 个人中心 → 余额区域点 **余额明细**。
2. 核对：当前余额 = 期初 + 之后每一笔流水的累加（顺序按账户内序号）；每行显示类型、带正负号的金额、变动后余额、关联订单。
3. 按类型（充值 / 下单扣款 / 订单退款 / 活动取消退款 / 期初余额）和时间范围筛选；点关联订单跳到订单详情。
4. 充值 €50 → 返回个人中心余额更新；余额明细自动出现一条「充值」。
5. 幂等充值：带同一 `Idempotency-Key` 重放充值请求 → 只入账一次；换一个键 → 正常入账（两笔不同的充值都成功）。

## 5. 通知与多设备刷新（Kafka + SSE）

1. 打开两个浏览器（或普通 + 无痕窗口）登录同一账号：窗口 A 停在「我的预订」，窗口 B 停在「个人中心」。
2. 在窗口 B 下单 / 结算。几秒内（Outbox → Kafka → Worker → Redis → SSE）窗口 A 的订单列表自动刷新出订单；窗口 B 的余额也自动更新。
3. 站内消息里能看到订单通知和充值通知；同一次支付不会出现「含义相同的两条提醒」。
4. **Kafka 故障演练**（可选）：`docker compose stop kafka`，再下一单——下单照常成功，只有通知延迟；`docker compose start kafka` 后，Worker 把 Outbox 里的积压消息投递出去，通知补齐。

## 6. 迁移与幂等（老环境升级路径）

```bash
# 1) 用旧版本 schema 制造老数据（V1 + 余额非 0 的账号 + 老订单）
# 2) 启动新版本 → Flyway 追加 V2：老账户出现一条「期初余额」，余额数值不变
# 3) 取消那张老订单 → 正常退款，余额明细里是「期初余额 + 订单退款」两行
```

集成测试 `WalletLedgerMigrationIT` 自动覆盖了这条路径；手工验收可跳过。

## 7. Seeder 幂等

```bash
make down && make up        # 重跑播种
```

`seed_runs` 保证同一版本只播种一次；重复 `make up` 不会出现重复订单、重复流水或余额变化。
