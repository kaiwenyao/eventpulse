# Plan: Close remaining plan-vs-implementation gaps in EventPulse backend

## Context (completion audit)
Baseline: **backend 113/113 tests pass, JaCoCo coverage 91.4% instructions / 90.8% lines** (`dev.kaiwen` namespace). ML `pytest` 3/3 pass. The detailed plan PDF was mapped item-by-item to code; 15 of 18 mandated capabilities are fully implemented and tested. Three **real Must-priority gaps** remain between plan and implementation. This PR closes all three, adds tests, and keeps coverage ≥90%.

## Gap 1 — Wire V1 (embedding) into recommendation ranking
**Problem:** `RecommendationService.recommend()` hardcodes `modelVersion = MODEL_V0` and never reads embeddings. `EmbeddingService.embedEvent()` runs in the seeder (so `events.embedding` is populated), but nothing consumes it — V1 ("text embedding + preference vector") is defined but not actually used.
**Fix:** In `recs/RecommendationService`:
- Add `embeddingService` field (already injected at ctor `RecommendationService.java:41`).
- In `recommend()`: set `modelVersion = embeddingService.isVectorAvailable() ? MODEL_V1 : MODEL_V0` (graceful degrade to V0 when pgvector absent).
- In `score()`: when V1, build a user preference vector by embedding the user's preferred categories (`embeddingService.embed(joined-categories)`), and add an embedding-similarity term via pgvector cosine distance `<=>` between the event `embedding` and the preference vector; add reason code `EMBEDDING_MATCH` when it contributes. Keep V0 popularity + filters as the base so ranking degrades cleanly.
**Test:** Extend `RecommendationApiIT` — seed events with embeddings (via seeder path / `embedEvent`), give a user a `user_preferences` row, assert `modelVersion == "v1-embedding"` and `EMBEDDING_MATCH` reason appears for a relevant event. Add a unit-level test on the scoring boost via an existing-style test.

## Gap 2 — Enforce interactions rate limit
**Problem:** `AppProperties.RateLimit.interactions` (`30/60`, `application.yml:94`) is configured but `RecommendationController.interactions()` never calls `rateLimiter.check`. Plan §8/§12 require rate limiting on interactions.
**Fix:** In `recs/RecommendationController`: inject `RateLimiter`, call `rateLimiter.check("interactions", actorKey)` at the top of `interactions()` where `actorKey = user != null ? user.id().toString() : "session:" + sessionId` (mirrors `redeem`/`reauth` usage). On limit exceeded it throws `RATE_LIMITED` (already handled by `GlobalExceptionHandler`).
**Test:** Extend `RecommendationApiIT.interactionsBatch...` to fire >30 batches in a loop and assert one returns 429; or add a focused test. (RateLimiter falls back to in-process window when Redis unavailable in tests.)

## Gap 3 — Mask sensitive fields in admin exceptions
**Problem:** Plan §2.3/§12 require "敏感字段脱敏" on the admin exception view. `AdminController.exceptions()` returns raw row maps including `provider_key`, `last_error`, `lease_owner`.
**Fix:** Add a small `mask(Map)` helper in `admin/AdminController` that truncates/masks long free-text columns (`provider_key`, `last_error`, `lease_owner`) to a fixed-length prefix + `…`, leaving identifiers/amounts intact. Apply it to each list returned by `exceptions()`.
**Test:** Extend `AdminApiIT` — assert a `MANUAL_REVIEW` command's `provider_key`/`last_error` in the exceptions response are masked (shorter than stored, or ends with the mask marker), while ids/amounts remain intact.
